    Maintainership

    Writing code starts a project; maintaining it keeps the project alive. A maintainer decides what gets in, keeps the issue tracker usable, turns first-time contributors into regulars, and makes sure the project can outlive any single person — including the maintainer. This lesson closes the roadmap with the work that usually decides whether an open source project thrives or quietly dies.

    The Maintainer's Role

    A maintainer is a person with the authority to merge changes and cut releases, and with the responsibility that comes with it. Most of the job is not writing code: it is reading, deciding, explaining and delegating. In a healthy project the maintainers write a shrinking share of the code over time, because their main product is a community that writes it with them.

    Learn to Say No

    Every merged feature becomes code the maintainers must understand, test, document and support for years. Declining a well-meant contribution is therefore part of the job, not a failure of it. Say no early, kindly and with a reason that points at the project's stated scope: "Thanks for this. It is outside what the project aims to do (see the Goals section of the README), so we will not merge it. A plugin would be a great home for it." A clear scope document turns a personal rejection into a shared rule.

    Issue Triage

    Triage is the process of turning a raw report into an actionable item — or closing it. Untriaged issues pile up, duplicates multiply, and real bugs hide among support questions. Triage regularly in short sessions rather than in rare, exhausting marathons.

    Run a Triage Workflow

    Every new issue should leave triage in one of a few clear states:

    1. Needs information — ask for versions, a minimal reproduction or logs, and label it so it can be closed if the reporter never replies.
    2. Duplicate — link the original and close; the discussion continues in one place.
    3. Not planned — out of scope or working as designed; close with a short explanation.
    4. Accepted — label it by type (bug, enhancement, docs) and by priority or area, so contributors can find it.

    The GitHub CLI makes a triage session fast from the terminal; other forges offer equivalent tools.

    # List open issues that have not been triaged yet.
gh issue list --label "needs-triage" --state open

# Accept a confirmed bug: classify it and take it out of the triage queue.
gh issue edit 123 --add-label "bug,area:parser" --remove-label "needs-triage"

# Close a duplicate with a pointer to the original discussion.
gh issue close 124 --reason "not planned" --comment "Duplicate of #98; please follow that issue."

    Collect Information Up Front

    Most triage time is spent asking for missing details. Issue forms ask for them before the issue exists. On GitHub, a file in .github/ISSUE_TEMPLATE/ defines a form with required fields, and can apply a triage label automatically:

    # .github/ISSUE_TEMPLATE/bug_report.yml
name: Bug report
description: Report something that does not work as documented.
labels: ["needs-triage"]
body:
  - type: input
    id: version
    attributes:
      label: Version
      description: Output of `tool --version`.
    validations:
      required: true
  - type: textarea
    id: reproduce
    attributes:
      label: Steps to reproduce
      description: The smallest input or script that shows the problem.
    validations:
      required: true
  - type: textarea
    id: expected
    attributes:
      label: Expected and actual behavior
    validations:
      required: true

    Add a config.yml in the same folder to point support questions to a forum or discussion board, keeping the issue tracker for bugs and agreed work.

    Backlog Hygiene

    A backlog of several thousand open issues is not a to-do list; it is noise. Contributors cannot find work, users cannot tell whether their problem is known, and maintainers stop reading. Keep the backlog small enough to be honest about what will actually happen.

    Close Issues Honestly

    Closing an issue is not the same as ignoring it: it is a clear answer. Close what you will not do, with a reason, and invite a pull request if the community wants it more than the maintainers do. Group accepted work into milestones tied to releases, so "when will this ship?" has a visible answer. Review the oldest open issues periodically and ask whether each is still true, still wanted, and still owned.

    Automate Carefully

    Stale bots can close issues that receive no activity, but they cut both ways: a bot that closes a confirmed, unfixed bug because nobody commented teaches users that reports are pointless. Limit automation to issues waiting on the reporter, and exempt anything maintainers have accepted:

    # .github/workflows/stale.yml: close only issues stuck waiting for the reporter.
name: Close unanswered issues
on:
  schedule:
    - cron: "30 3 * * 1"   # every Monday at 03:30 UTC

permissions:
  issues: write

jobs:
  stale:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/stale@v9
        with:
          # Only issues labelled as needing information are eligible at all.
          only-labels: "needs-info"
          days-before-stale: 21
          days-before-close: 14
          stale-issue-message: >
            This issue is waiting for the information requested above.
            It will close in two weeks without a reply; it can be reopened at any time.
          # Never touch pull requests with this workflow.
          days-before-pr-stale: -1
          days-before-pr-close: -1

    Contributors and Retention

    Most contributors make one contribution and leave. Projects that last convert a few of them into regulars, and a few regulars into maintainers. The single strongest factor is how the first contribution is received.

    Lower the Barrier to the First Contribution

    • A CONTRIBUTING.md that explains how to build, test and submit a change in a few commands (see Documentation).
    • A good first issue label on small, well-described tasks, with a pointer to the relevant code. Writing such an issue takes longer than fixing it yourself; that is an investment, not a waste.
    • Fast first responses. A short "thanks, I will review this week" within a couple of days matters more than a quick merge.
    • Automated checks that explain failures, so a contributor can fix formatting or tests without waiting for a human (see CI/CD Basics).

    Grow New Maintainers

    Recognize repeat contributors publicly: in release notes, in an AUTHORS or contributors file, and in the project's channels. Then delegate real responsibility in steps — triage permissions first, review duties next, merge rights last. Write down how someone becomes a maintainer, so promotion is based on visible criteria rather than on who happens to know the founder.

    Governance and Conduct

    Every project has governance, even if it is only "the founder decides". Writing it down makes decisions predictable and disputes resolvable. GitHub surfaces several of these files in a repository's community profile.

    Publish the Community Files

    FileAnswers the question
    CODE_OF_CONDUCT.mdHow must people behave, and how are violations reported and handled? Many projects adopt the Contributor Covenant.
    GOVERNANCE.mdWho decides, how are disagreements resolved, and how do people gain or lose roles?
    CONTRIBUTING.mdHow do I propose and submit a change?
    SECURITY.mdHow do I report a vulnerability privately, and which versions are supported?

    A code of conduct only helps if it is enforced. Name who receives reports, respond to them privately, and act consistently — including when the person involved is a prolific contributor.

    Handle Security Reports Privately

    A vulnerability reported in a public issue is disclosed to attackers before users can patch. SECURITY.md should give a private channel — an email address or the forge's private vulnerability reporting feature — and a response time. Acknowledge the report, confirm and fix it in private, publish a patched release, and then disclose with an advisory that credits the reporter. The Open Source Security Foundation publishes guides for maintainers on coordinated vulnerability disclosure.

    Sustainable Stewardship

    The most common way open source projects fail is not a bad design decision; it is a tired maintainer who stops answering. Sustainability is a technical requirement, because a project with no active maintainer cannot ship security fixes.

    Raise the Bus Factor

    The bus factor is the number of people who would have to disappear before the project stalls. Raise it on purpose: at least two people with publishing rights to the package registry, credentials stored in a shared secret manager rather than one laptop, documented release steps, and review duties spread across several people. If you plan to step down, say so publicly, hand over to a named successor, or mark the repository as archived and unmaintained so users can make informed choices.

    Protect the Maintainers

    Set expectations publicly: state the hours or response times maintainers can offer, and that the project comes with no warranty or obligation, as its license already says. Batch notifications instead of reacting to every event. Accept that some issues will wait. Where a project is widely used, funding channels such as sponsorship platforms or foundations can pay for maintenance time, infrastructure and security audits. Asking users who depend on the project to contribute back is reasonable, not rude.

    Practice Lab

    Use one of your own repositories, or volunteer to help triage on a project whose maintainers welcome it — many list this in their contributing guide.

    Run a Triage Session

    1. Create the labels needs-triage, needs-info, bug, enhancement and good first issue.
    2. Add a bug-report issue form that applies needs-triage automatically, and open a test issue through it.
    3. Spend thirty minutes triaging: move every issue to one of the four states above, with a comment explaining each decision.
    4. Write two good first issue entries detailed enough that a stranger could complete them without asking a question.

    Audit Project Health

    1. Check the repository's community profile and add any missing community file from the table above.
    2. Write a SECURITY.md with a private reporting channel and the supported versions from your release policy.
    3. List everything only one person can do today — publish, deploy, rotate a secret — and give each item a second owner or written instructions.
    4. Write down how a regular contributor becomes a maintainer, and add it to GOVERNANCE.md.
