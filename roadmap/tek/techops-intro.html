    TechOps Fundamentals

    Software creates value only while it runs. Technical operations (TechOps) is the work of keeping systems available, fast, secure and affordable after they ship — and of making each change to them safe. This opening lesson sets out the mindset, the roles, the language of service levels, and a way to measure how mature an operation is. The rest of the roadmap teaches the skills, from Linux to SRE practices.

    The Operations Mindset

    Developers ask does it work? Operators ask does it keep working — at 3 a.m., under ten times the load, after a disk fills, when a dependency is slow, and after the next deploy? Both questions matter; TechOps makes the second one routine.

    Core Principles

    • Everything fails eventually. Design for failure of disks, servers, networks, zones and people, and decide in advance what happens when each fails.
    • Automate the repeatable. A task done by hand twice should be scripted; a script run by hand every week should be scheduled or triggered.
    • Make change safe, not rare. Small, frequent, reversible changes cause fewer and shorter incidents than large, infrequent ones.
    • Measure from the user's side. A green server dashboard means little if users see errors.
    • Write it down. Runbooks, diagrams and decisions in version control outlast any one person's memory.

    TechOps, DevOps and SRE

    The terms overlap. DevOps is a culture and set of practices that removes the wall between building and running software, so the same team owns both. Site Reliability Engineering (SRE), popularized by Google, applies software engineering to operations problems and manages reliability with explicit targets and error budgets. Platform engineering builds internal tools and paved paths that let product teams deploy and operate on their own. This roadmap uses TechOps for the shared body of skills all of them need.

    Roles and Team Interfaces

    Operations work exists in every organization; what differs is who does it and how teams hand work to each other.

    Operating Models

    ModelHow it worksRisk
    Separate ops teamDevelopers hand releases to operators, who run them.Slow handoffs; operators run code they cannot change.
    You build it, you run itProduct teams operate their own services, including on-call.Duplicated tooling; uneven skills across teams.
    Platform + product teamsA platform team provides shared infrastructure as a product; product teams self-serve.The platform must be good enough that teams choose to use it.
    Embedded SREReliability engineers work inside or alongside product teams on the hardest services.Scarce skills; needs clear engagement rules.

    Define Clear Interfaces

    Whatever the model, write down the interfaces between teams: how to request infrastructure, what a service must provide before it goes to production (health checks, dashboards, runbooks, an owner), who is paged for what, and how incidents are escalated. A short production readiness checklist agreed by all teams prevents most “who owns this?” moments during an outage.

    Service Levels: SLAs, SLOs and SLIs

    Reliability conversations go nowhere without numbers. Three related terms give them a shared vocabulary.

    Definitions

    TermMeaningExample
    SLI — indicatorA measured property of the service as users experience it.Share of HTTP requests answered successfully in under 300 ms.
    SLO — objectiveAn internal target for an SLI over a time window.99.5% of requests over 30 days.
    SLA — agreementA contract with customers, with consequences such as refunds if missed.99.0% monthly availability, or service credits.

    Set SLOs stricter than SLAs, so the team is alerted and reacts long before a contract is breached.

    What the Nines Cost

    Each extra “nine” of availability cuts the allowed downtime by a factor of ten, and usually multiplies the cost and effort required:

    AvailabilityDowntime per 30 daysDowntime per year
    99%7.2 hours3.65 days
    99.9%43.2 minutes8.77 hours
    99.99%4.3 minutes52.6 minutes
    99.999%26 seconds5.3 minutes

    At 99.99%, a human cannot even be paged and log in within the budget; recovery must be automatic. Choose the target the users actually need, not the highest one that sounds good. The SRE Practices lesson shows how to spend the remaining error budget.

    Operational Maturity

    Teams improve operations in recognizable stages. Knowing the current stage helps choose the next investment rather than copying practices built for a different scale.

    A Simple Maturity Model

    1. Reactive: servers configured by hand, users report outages, knowledge lives in a few heads.
    2. Repeatable: scripted deployments, basic monitoring and alerting, some runbooks.
    3. Defined: infrastructure as code, CI/CD with automated tests, on-call rotation, post-incident reviews.
    4. Measured: SLOs and error budgets steer priorities; toil is tracked and reduced.
    5. Optimizing: failure is rehearsed (game days, chaos experiments), and reliability improvements are designed in.

    Measure Delivery Performance

    The DORA research program identified four metrics that predict both delivery speed and stability: deployment frequency, lead time for changes, change failure rate, and time to restore service. The research consistently found that speed and stability improve together rather than trading off. Track these four from the start; they show whether operational changes are actually helping. The annual DORA reports publish benchmarks.

    The Daily Work of Operations

    Operations work falls into a few recurring categories. Healthy teams protect time for the last one.

    Kinds of Work

    • Interrupts: pages, tickets, access requests and questions from other teams.
    • Changes: deployments, configuration updates, patching and upgrades.
    • Toil: manual, repetitive work that grows with the system and has no lasting value — the main target for automation.
    • Engineering: projects that permanently improve reliability, security or efficiency.

    Change Management Without Bureaucracy

    Most outages are caused by changes. The answer is not a weekly approval board but changes that are small, peer-reviewed, tested by automation, rolled out gradually and easy to roll back. Record every change — deploys, configuration edits, feature-flag flips — in a single timeline, so the first question in an incident, what changed?, has a quick answer.

    Practice Lab

    Pick a service you use or run: a personal website, a school project, or a public API.

    Define Service Levels

    1. Write two SLIs for it, one for availability and one for latency, stating exactly where each would be measured.
    2. Choose an SLO for each and calculate the error budget in minutes per month.
    3. List three failures that would consume the budget, and what would detect each one.

    Write a Readiness Checklist

    1. Draft a ten-item production readiness checklist: owner, health check, dashboards, alerts, runbooks, backups, rollback, and so on.
    2. Score the service against it and rank the gaps by risk.
    3. Place the service in the maturity model above and name the one practice that would move it up a level.
