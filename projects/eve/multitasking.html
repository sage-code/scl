Eve Multitasking

Multitasking means that several pieces of work make progress together. Eve has two tools for it. Generators produce values one at a time and let tasks take turns on one core, at the points marked with yield. Parallel aspects run on several cores: the driver starts them in a parallel group, and they exchange data through output parameters, at the barrier that closes the group, or through channels while they run. Methods and functions always run in serial mode, on the core of their caller. Eve has no coroutines, no async and no await. It assumes the Methods chapter. This chapter explains generators, parallel groups, the data rules, Bulk Synchronous Parallel, channels and how to choose a model.

Generators

Designed, not in Eve 0.1: generators and the module task are specified and implemented in version 2. The keyword yield is reserved.

A generator is a method that produces its values one at a time. It gives a value to its caller, waits, and continues from the same place when the caller asks for the next value. Its local variables keep their values between two requests. A generator is useful for long or infinite sequences, for reading data step by step, and for tasks that take turns on one core.

Declaration

A method becomes a generator when its body contains yield. It declares one result, the value it produces. A function can't contain yield: a function has no state.


** produce the numbers 1 to n, one at a time
method count_to(n: Integer) => (@x: Integer) is
  for i in (1..n) do
    x := i;           ** set the result
    yield;            ** give x to the caller, wait here
  done;
return;               ** no more values
  • yield; gives the current value of the result to the caller and suspends the generator. This is the explicit form;
  • yield expression; is the short form of x := expression; yield;. Both forms are valid;
  • return; ends the generator: the caller sees that there are no more values;
  • A generator can be infinite, with while True do … yield; done;: the caller decides when to stop;
  • A generator can be a method of a class: method walk(@self) => (@node: Node) is … return;.

Use

A call of a generator does not run its body. It creates a generator object of the core class Generator(:T), where T is the type of the result. The body runs only when the caller asks for a value. There are three ways to ask:


** 1. a for loop takes the values one by one
for v in count_to(5) do
  print v;                         ** 1 2 3 4 5
done;

** 2. a comprehension collects all the values
let squares := (v * v | v in count_to(5));   ** (1, 4, 9, 16, 25)

** 3. a generator object driven step by step
let g := count_to(3);              ** nothing runs yet
while g.next() do                  ** run to the next yield
  print g.value;                   ** the value given by yield
done;
MemberMeaning
g.next()run the body to the next yield: True and a new g.value; False when the body has returned
g.valuethe last value given by yield; reading it before the first next() is an error
g.doneTrue after the body has returned or after close()
g.close()stop the generator early and drop its state

A generator object is not created with new: new is for the objects of a class. A generator called as a statement, count_to(5);, is an error, because its values would be lost.

Rules

  1. One level: yield is allowed only in the body of the generator itself, not in a method or function it calls, not in a lambda and not in a process. A method called by the generator runs to completion. A generator that uses the values of another one loops over it and gives them again: for c in child.walk() do yield c; done;. This rule makes a generator simple: it is not a coroutine, and Eve has no coroutines;
  2. Lazy: the arguments are evaluated when the generator object is created; the body begins at the first request;
  3. State: the parameters and the local variables live in the generator object between two requests. They are dropped when the body returns, at close(), or when nobody refers to the object any more. A for loop left with break closes its generator;
  4. Parameters: a generator receives inputs only, by value. It has no "@" parameters other than its result;
  5. Errors: an error raised in the body ends the generator and is raised in the caller, at the next() or at the for line, where the recover region of the process can handle it;
  6. One owner: a generator object is never copied. Passing it to a method shares the same object. It can't be an argument of apply or start: it belongs to one process and runs on the core of its caller.

Cooperative tasks

Generators are also the cooperative tasks of Eve. Each generator is a task, and each yield is a point where the task lets the others run. A loop in the caller gives the turns. Everything runs on one core, in a fixed order, so the result is the same on every run and no data needs protection.


# two tasks take turns on one core
driver ping_pong is
  method ping(n: Integer) => (@step: Integer) is
    for i in (1..n) do
      print "ping";
      yield i;                     ** let the other task run
    done;
  return;

  method pong(n: Integer) => (@step: Integer) is
    for i in (1..n) do
      print "pong";
      yield i;
    done;
  return;

  process main is
    let a := ping(3);
    let b := pong(3);
    while not (a.done and b.done) do
      a.next() if not a.done;
      b.next() if not b.done;
    done;                          ** ping pong ping pong ping pong
  return;
end ping_pong;

The library module task (version 2) gives the turns for you:

MethodMeaning
task.round_robin(tasks);run a list of generators in turns, one step each, until all of them are done
task.until(g, condition);run one generator step by step until the condition is true or the generator is done
 

  task.round_robin((ping(3), pong(3)));   ** same output as the loop above

Generators and channels

A generator runs on the core of its caller, so it can't feed a started aspect directly. To send the values of a generator to parallel workers, a started producer aspect creates the generator and sends its values into a channel: for v in source() do jobs.send(v); done;. Channels are explained below.

Parallel aspects

Not in Eve 0.1. Parallel groups and channels are designed but not implemented in version 1; their keywords are reserved. In version 1 an aspect is only applied, and it runs on the core of its caller.

Eve does parallel work with aspects. An aspect is an encapsulated machine: it has one process, main, and nothing public. apply name(args); runs it in serial mode and the caller waits. start name(args);, written in a parallel group of the driver, runs it on a worker core. Methods and functions always run in serial mode, on the core of their caller: they can't be started. These are the concepts:

  • Driver: the master. Its process main runs on one core and is the only place where parallel groups are allowed; it opens them one after the other;
  • Parallel group: a block parallel … do … done that starts aspects and waits for all of them;
  • Task: one aspect started with start. It runs on a worker core with its own state, created at start and dropped when its main returns, and with its own copy of the input arguments;
  • Barrier: the closing done. The driver waits there until every task of the group has returned; then the outputs (@) are ready;
  • Channel: a queue that connects tasks running at the same time. A task sends values into it, another task receives them.

With these elements Eve supports three models of parallel work: task groups (different aspects side by side), Bulk Synchronous Parallel (the same aspect on slices of the data, in supersteps) and pipelines (stages connected by channels). An aspect can't apply or start another aspect, so the work of a task is done by its own methods and functions, and by the modules it imports.

Parallel groups

A parallel group starts aspects that run at the same time. The driver executes the groups one by one: a group begins after the previous group has finished. Each group can have an optional label.

Syntax:


[label:] parallel
  ** declarations, local to the group
do
  start aspect_name(arguments);
  ...
done [label];

parallel … do … start … done

Example: task group

The work of one worker is an aspect, in its own file task.eve:


# work done by one worker
aspect task is
  process main(n: Integer) is
    print ("task ", n, " is running");
  return;
end task;

The driver starts it four times, in two groups:


# parallel groups demo
driver parallel_demo is
  process main is
    ** the driver is a series of sequential groups
    group1: parallel
      ** local variables for group1
    do
      start task(1);
      start task(2);
    done group1;

    ** group1 is now complete, group2 starts
    group2: parallel
      ** local variables for group2
    do
      start task(3);
      start task(4);
    done group2;

    ** Both groups are now complete
  return;
end parallel_demo;

Notes:

  • Each group executes sequentially. Within a group, the started aspects run at the same time, on several cores;
  • A parallel group is allowed only in the process main of the driver, and groups are not nested. start is allowed only in the do region of a group, and it starts only aspects: start method() is an error;
  • The do region can use control statements, for example a loop that starts the same aspect several times;
  • The closing done waits for all the aspects started in the group, and it is always for a single group;
  • The label of a group is optional. A group without a label starts with parallel and ends with a naked done;; a labeled group ends with done label;.

The driver can start the same aspect several times with different arguments, to compute different parts of the data. Every started aspect writes its own element of the array s: two started aspects never receive the same output variable.


# compute one result
aspect square is
  process main(n: Integer, @result: Integer) is
    result := n * n;
  return;
end square;


## create parallel work
driver parallel_loop is
  process main is
    let s: [4]Integer; ** one result for each worker

    ** start the same aspect 4 times
    demo: parallel
    do
      for i in (1..4) do
        start square(i, @s[i]); ** runs in parallel
      done;
    done demo;
    ** all started aspects have finished, s is ready
    print s; ** [1,4,9,16]
  return;
end parallel_loop;

Data rules

Tasks run at the same instant, so two tasks must never write the same data. Eve guarantees this with a few rules; it needs no locks and no shared mutable objects, except channels.

  • Inputs by value: the arguments are evaluated at start. An argument without "@" is passed by value, also a collection: the task works on its own copy, and the driver can go on changing its variables. The virtual machine shares a large collection and copies it only when one side writes into it (copy on write), so passing by value is cheap;
  • One owner for each output: an output argument (@) is passed by reference and belongs to one task. Two tasks of the same group can't receive the same variable, the same element or two overlapping slices as output. The compiler rejects what it can prove; the virtual machine checks the rest at start and raises an error;
  • Channels are the exception: a channel is the only object that several tasks of a group can receive with "@". It is built for that: its operations are safe when tasks use it at the same time;
  • Encapsulated: an aspect sees no globals of the driver and has no public members; its state belongs to one task. It calls its methods by name, and they run on the same worker. It can print, but the lines of different tasks come in any order;
  • No nesting: only the driver opens parallel groups; an aspect can't apply or start another aspect.
  • Modules are shared: all the tasks use the same copy of a module. Its public constants, classes, functions and methods are safe to share, and a public channel of a module connects tasks without being passed as a parameter. A started aspect can't change the private variables of a module (see Modules and parallel aspects).

Errors and time-out

  • A parallel group behaves like a job. When a task raises an error, the other tasks go on; done waits for all of them, then raises the first error in the driver, where $error.job is the label of the group. In recover, retry runs the whole group again and resume continues after it; without recover the next groups do not begin;
  • A task that waits on a channel longer than $timeout (60 seconds by default, set in the configuration file of the driver) raises a time-out error;
  • When every unfinished task of a group waits on a channel, nothing can move any more: this is a deadlock. The virtual machine detects it and raises a deadlock error at done.

Workers

The number of started aspects is not limited by the number of cores. The virtual machine keeps a pool of worker threads, one for each core, and queues the extra tasks. The pool size is the system variable $cores: by default the number of hardware cores, it can be set in the configuration file of the driver.

A waiting aspect gives its core away. A started aspect that waits, for a file, the network, a database, a wait 10ms; or a channel, releases its worker to another task and continues when the wait is over. The virtual machine does this; the code of the aspect stays plain sequential code. So a group can start more aspects than there are cores and overlap their waits: calling 50 services is one group of 50 started aspects on a few cores, and a pipeline with more stages than cores still works.

The number of tasks can be dynamic. You can read it from the configuration file, compute it from the size of the data or from $cores, or hard code it as a constant inside the driver. This gives you flexibility to tune your driver.

Bulk Synchronous Parallel

The recommended pattern for parallel work is Bulk Synchronous Parallel (BSP). The computation is a sequence of supersteps. A superstep has three phases:

  1. Compute: every worker computes on its own part of the data, without talking to the others;
  2. Communicate: every worker writes its results into its own output;
  3. Synchronize: a barrier waits for all the workers. After the barrier, all the results are visible.

In Eve, one parallel block is one superstep, and its done is the barrier. Between two blocks the driver runs alone: it combines the partial results or prepares the data for the next superstep. An iterative algorithm puts the parallel block in a loop.

Example: parallel sum

Next driver computes the sum of 32,000 random numbers with 32 workers. The data is split into 32 slices, one for each worker, and every worker writes one element of the array partials. The worker is the aspect partial_sum:


# local computation: one slice in, one partial sum out
aspect partial_sum is
  process main(data: []Integer, @partial: Integer) is
    partial := 0;
    for x in data do
      partial += x;
    done;
  return;
end partial_sum;


# parallel sum with one BSP superstep
driver parallel_sum is
  set workers = 32 :Integer;
  set size = 1000 :Integer; ** elements for one worker

  process main is
    let data: [workers * size]Integer;
    let partials: [workers]Integer;

    ** produce the data
    for i in (1..workers * size) do
      data[i] := (0..99).random();
    done;

    ** superstep: 32 workers, one slice each
    sums: parallel
      let first: Integer;
    do
      for w in (1..workers) do
        first := (w - 1) * size + 1;
        start partial_sum(data[first..first + size - 1], @partials[w]);
      done;
    done sums; ** barrier: all the partial sums are ready

    ** combine on the main core
    let total := 0;
    for p in partials do
      total += p;
    done;
    print total;
  return;
end parallel_sum;

The same job can be written as a pipeline, with a producer, 32 consumers and channels between them (see Channels). For data that is already in memory, the BSP version is simpler and safer:

  • no shared object: every worker reads its own slice and writes its own element;
  • no blocking: a worker never waits for another worker, only the driver waits, at done. There is no buffer that can fill up, so there is no deadlock;
  • deterministic: the partial results are combined in index order, so the result is the same on every run, also for floating point numbers, where the order of a sum changes the rounding;
  • one error point: errors arrive at the barrier, where the recover region of the driver can handle them;
  • predictable cost: a superstep lasts as long as its slowest worker, plus the barrier.

Example: iterative supersteps

Next driver simulates the heat that flows along a bar. The bar is an array of 1002 cells. The first cell is hot and the last cell is cold; they don't change. At every step, a cell takes the average of itself and its two neighbors. The 1000 inner cells are split into 10 slices. A worker, the aspect smooth, receives the current state cur by value and writes its slice of the next state nxt by reference. After the barrier the driver clones nxt into cur with ::; an assignment := would share the array instead of copying it, and the next superstep would read and write the same cells. This copy is the communication between supersteps: in the next superstep every worker sees the new values of its neighbor slices.


# compute one slice of the next state
aspect smooth is
  process main(cur: []Real, first: Integer, @part: []Real) is
    for k in (1..part.count()) do
      let i := first + k - 1;
      part[k] := (cur[i - 1] + cur[i] + cur[i + 1]) / 3;
    done;
  return;
end smooth;


# heat diffusion with iterative BSP supersteps
driver heat_bar is
  set workers = 10 :Integer;
  set width = 100 :Integer; ** cells for one worker

  process main is
    let cur: [workers * width + 2]Real;
    let nxt: [workers * width + 2]Real;
    cur[1] := 100.0; ** hot end, the cold end stays 0
    nxt[1] := 100.0;

    for n in (1..500) do
      ** compute in parallel
      superstep: parallel
        let first: Integer;
      do
        for w in (1..workers) do
          first := (w - 1) * width + 2;
          start smooth(cur, first, @nxt[first..first + width - 1]);
        done;
      done superstep; ** barrier

      ** communicate: the next state becomes the current state
      cur :: nxt; ** clone: cur is a new copy of nxt
    done;
    print cur[2..11]; ** temperature near the hot end
  return;
end heat_bar;

Channels

A channel is a queue with a fixed capacity that connects tasks running in the same group. A producer task sends values into the channel; a consumer task receives them in the same order. When the channel is full, the sender waits; when it is empty, the receiver waits. In this way a fast stage can't run away from a slow one, and data flows through the tasks while it is produced. This is the right tool for streams: data that arrives over time or does not fit in memory.

Create a channel

Channel(:T) is a generic class of the core library. The type parameter is the type of the values; the constructor takes the capacity and, optionally, the number of senders.


  let jobs := new Channel(:Integer)(capacity: 100);
  let results := new Channel(:Real)(capacity: 100, senders: 4);

Operations

OperationMeaning
ch.send(value);put a value at the end of the channel; wait while the channel is full. Sending into a closed channel is an error
for x in ch do … done;receive the values one by one, waiting for each; the loop ends when the channel is closed and empty
ch.receive(@x);receive one value into x; wait while the channel is empty. Receiving from a closed, empty channel is an error
ch.close();a sender has finished. With senders: n the channel closes after the n-th close; without it, after the first
ch.count()the number of values waiting in the channel, for monitoring

Rules:

  • A channel is created by the driver, before the group or in the declarations of the group, and it is passed to the tasks with "@": start produce(@jobs);. The parameter of main is declared @jobs: Channel(:Integer);
  • Every sender must close the channel when it has finished, otherwise its receivers wait forever (until the time-out). With several senders, create the channel with senders: n, so the receivers stop after the last sender;
  • Values sent into a channel are copied, like arguments passed by value: a receiver never shares data with the sender;
  • The order of the values from one sender is kept. With several senders the values are interleaved in any order, so a result that depends on the order is not deterministic;
  • After done all the tasks have finished. The driver can still read what is left in a closed channel with for x in ch do, but it is better to collect the results inside the group, as below.

Example: pipeline

Next driver has three stages, each one an aspect. One producer sends 10,000 random numbers into jobs. Four workers receive from jobs, square every number and send it into results. One collector receives from results and adds the values into total. The three stages run at the same time, and the barrier done flow waits for all six tasks.

produce → jobs → square ×4 → results → collect


# stage 1: produce the numbers
aspect produce is
  process main(count: Integer, @jobs: Channel(:Integer)) is
    for i in (1..count) do
      jobs.send((0..99).random()); ** waits while jobs is full
    done;
    jobs.close(); ** no more numbers
  return;
end produce;


# stage 2: square every number
aspect square is
  process main(@jobs, @results: Channel(:Integer)) is
    for x in jobs do ** ends when jobs is closed and empty
      results.send(x * x);
    done;
    results.close(); ** one of the 4 senders has finished
  return;
end square;


# stage 3: collect the results
aspect collect is
  process main(@results: Channel(:Integer), @total: Integer) is
    total := 0;
    for y in results do ** ends after the 4th close
      total += y;
    done;
  return;
end collect;


# pipeline: producer, 4 workers and a collector
driver pipeline is
  set workers = 4 :Integer;

  process main is
    let total: Integer;
    let jobs := new Channel(:Integer)(capacity: 100);
    let results := new Channel(:Integer)(capacity: 100, senders: workers);

    flow: parallel
    do
      start produce(10000, @jobs);
      for w in (1..workers) do
        start square(@jobs, @results);
      done;
      start collect(@results, @total);
    done flow; ** barrier: all the stages have finished

    print total;
  return;
end pipeline;

Notes:

  • The capacity limits the memory: at most 100 numbers wait in each channel, whatever the size of the stream;
  • The collector runs inside the group. If the driver tried to read results after done, the workers would wait on a full channel and the group would never end: the virtual machine would report a deadlock;
  • Only the collector writes total, so the output rule (one owner) holds;
  • A sum does not depend on the order of the values. For results that do, send an index with each value, or use BSP.

Choosing a model

ModelShapeShared dataResultUse it for
Generatorone method gives its values one at a time to its callernone: the generator keeps its own statedeterministiclong or infinite sequences, reading data step by step, lazy pipelines in one process
Cooperative tasksseveral generators take turns on one core, at each yieldnone: one core, a fixed orderdeterministicinterleaved steps: simulations, protocols, polling several sources
Task groupdifferent aspects side by side, one barriernone: inputs by value, one owner for each outputdeterministicindependent jobs: read several files, call several services, build several reports
Bulk Synchronous Parallelthe same aspect on slices of the data, a barrier after each superstepnone; data is exchanged by the driver between superstepsdeterministicdata in memory: aggregations, arrays and matrices, iterative algorithms
Pipelinestages connected by channels, running at the same timechannels onlyorder not guaranteed with several sendersstreams: data that arrives over time or does not fit in memory, input and output overlapped with computing

Inside one process, use a generator for a sequence and cooperative tasks for steps that take turns. For work that needs several cores, or many waits at the same time, start with a task group or BSP: a worker never waits for another worker, so they can't deadlock and they give the same result on every run. Use channels when the data is a stream. A driver can combine the models: for example a pipeline that reads a large file in one group, then BSP supersteps on the data it has collected.
