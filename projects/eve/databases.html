Eve Database/SQL

Eve has a database layer of its own: an ORM aligned with the object model of the language, SQLite as the core database and cache, and direct SQL for everything else. A record class says what a row is, a table declaration says where the rows live, and a job is a transaction. Structure changes (DDL) go through SQL scripts, never through the ORM.
Designed for version 0.4 (level 5). The rules on this page are the proposals of the design notes, waiting for the review of the author; the specification is spec/library/database.md. Reading files and writing reports is on the page Files and ETL.

Goals:

  • Read and update tables with records, writing only the fields that changed;
  • Stop hard when the code and the database disagree, before a row is written with a wrong mapping;
  • Make a job a transaction with commit, rollback and rules for retry;
  • Load, transform and transfer data between files and databases (ETL);
  • Run the same code on a local SQLite file, a database server or a database behind an Eve server.

A script reaches a database by a connection name, such as "sales". The name is declared in the configuration file of the machine, eve.cfg, with a URL. The script never sees the URL, the driver or the password, so the same code runs on every path:

Passwords are never written in scripts. They are secrets of the configuration of the machine (see System Library).

SQLite is the core

SQLite is part of the virtual machine. It needs no server, it is always there, and the tests of level 5 run on it. Each machine keeps its files in the folder db/:

RoleFileContent
Eve databasedb/eve.dbrun history, checkpoints, lineage, the journal of transactions
Cachedb/cache.dbcopies of remote reference tables, kept by the Eve server
Stagingdb/stage.db, connection "stage"temporary tables of an ETL run
Application datadb/<name>.dbsmall applications and services; db create <name>

One file per role keeps the locks apart: a long load into the staging file never blocks the run history. The VM opens SQLite in WAL mode with foreign keys on, and makes the tables it creates STRICT, so a text can not hide in an integer column.

Records

A row type is a class derived from Record. The class holds the fields; it knows nothing about a database:


class Customer = {id: Integer, name: String, city: String?, version: Integer} <: Record;
class Order    = {id: Integer, customer_id: Integer, amount: Decimal, created: Instant} <: Record;
  • A field of type String? may hold null (a nullable column). A field of type String never does;
  • A record made by a literal, {id: 0, name: "Ann", city: null, version: 0} :Customer, is detached: plain data, unknown to any database;
  • A record class may have methods. The method validate runs before every write (see Validation).

The table declaration

A table declaration binds a record class to a table of a connection. It declares a name, for example customers, that is an object of the library class Table(:Customer): the table seen as a buffer of records. A class hosts only methods, so the mapping is not in the class; one class can have several declarations (a file, a staging table, a remote table).


table customers: Customer in "sales" is
  key (id);                      ** the primary key, one field or several
  generated (id);                ** filled by the database: never written, read back after insert
  version version;               ** optimistic lock, checked and increased by every update
  column name as "cust_name";    ** a field whose column has another name
end customers;

table orders: Order in "sales" is
  key (id);
  generated (id, created);
  reference customer_id to customers;   ** a foreign key: orders are written after customers
end orders;

table countries: Country in "sales";    ** short form: key (id), nothing else
ClauseMeaning
in "name"the connection of eve.cfg; "eve" is the Eve database
as "schema.table"the name in the database, when it is not the declared name
key (f, ...)the primary key or a unique key; (id) when the class has a field id
generated (f, ...)columns that the database fills: identity, default, trigger
version fan integer or timestamp column for optimistic locking
column f as "name"a field whose column has another name
reference f to ta foreign key: orders the writes, is validated

temporaryonly in "eve" and "stage": the VM creates the table from the class
cached 1hthe Eve server keeps the table in its cache and refreshes it every hour (version 0.5)

table is a contextual keyword: a keyword only at the start of a declaration. A field named key or version is still allowed. A table is declared in a driver, an aspect, a module or a macro, like a class.

Column = value mapping

The column of a field is its name, or the name of a column ... as clause. There is no case conversion and no plural rule: Eve quotes every name in the SQL, so CustName matches only CustName. When only the case differs, the message tells you the clause to write; Eve never guesses.

A pair outside the table, such as a String field and a numeric column, is a mapping error. So is a pair that could lose data, such as an Integer field and a numeric(30) column: a mapping must be safe for every row, not only for the rows of today.

The compiler turns each declaration into a plan, the ordered list of fields and columns. Eve never writes select *: it reads the columns of the plan in order, and the values of an insert or an update are always parameters, never text inside the SQL.

Debug mode reports, production refuses

Eve checks the code against the real database: the table exists, every field has its column, the types match without loss, a nullable column has an optional field, a column that is NOT NULL without default has a field, the key is a real key.

  • Debug mode (eve -d): the compiler connects to every database named by a table and lists all the differences of all the tables in one run, each with the line of the declaration and a fix, or the whole class and table text generated from the database (db describe sales orders --eve). Errors stop the compilation; warnings, such as a column the class does not use, are printed. After a clean run, the compiler writes a fingerprint of each table to db/mappings.json, which you commit with the code;
  • Production mode (the default): the compiler does not connect, because the production database is usually not reachable from where the code is built. When the VM opens a connection for the first time, before the first statement, it reads the catalog of the mapped tables and runs the same checks. A difference is a MappingError: the program stops before it has read or written a row. retry and resume are refused for it, the process aborts with exit code 4. The schema will not repair itself, and a retry loop would only hammer the database.

A value that can not be converted at run time, such as a text that is not a UUID, is a ConvertError with the table, the column and the key of the row.

Sessions and tracked records

The first use of a connection name in a process opens a session: the connection, its transaction and the records it tracks. Each process has its own sessions, so each aspect has its own connections and a started aspect never shares one with its siblings. A session is never shared state, so loading in parallel needs no special rule.

A record read with find! or where! is tracked. It remembers the original value of every field you change:

StatusMeaning
detachedunknown to a session (made by a literal)
addedwaiting to be inserted
cleanread from the database and not changed
dirtyat least one field differs from the value read
removedwaiting to be deleted
stalean update found another version in the database

Setting a field back to its original value makes the record clean again. A record with no changed field writes nothing. You read the status with customers.status(c).

Methods of a table

The names follow one rule: a ! marks a result that can change from call to call. Every read of a database is one, so find!, where!, scan! and count! carry it. A write that returns nothing has no ! (add, remove, flush), and a write that returns counts keeps it (load!, execute!). The mark says nothing about parallel use: the compiler decides that.

Append


new c := {id: 0, name: "Ann", city: null, version: 0} :Customer;
let customers <+ c;               ** status: added; nothing is sent yet

At the end of the job one insert is sent. The generated fields are left out of the statement and read back: after the job, c.id holds the number given by the database.

Update


new c := customers.find!(42);
let c.city := "Lyon";             ** the field is dirty, the original value is kept

An assignment to a field of a tracked record is already the update: there is no block to write. The statement sent writes only the fields that changed, and checks the version:

update "customers" set "city" = ?, "version" = "version" + 1
where "id" = ? and "version" = ?

Ten thousand records with the same changed field are sent as one batch, not as ten thousand statements. Changing a key field, a generated field or a field of a read only table is an error; changing a key is a delete and an insert.

Delete


customers.remove(c);              ** status: removed; delete at the end of the job

At the end of the job Eve writes in a safe order: inserts first (customers before orders, from the reference clauses), then updates, then deletes in the reverse order (orders before customers). A cycle of reference clauses is a compile error.

Validation

A record class can check itself. The method validate runs before every insert and update, and a failure is an error of the job with the key of the record in the message:


class Product = {id: Integer, price: Decimal, version: Integer} <: Record is
  method validate(@self) is
    expect self.price > 0d;
  return;
end Product;

Transactions: a job is a transaction

You do not write begin. The first statement of a job that uses a connection begins a transaction on it. At done or stop the job writes the pending changes, then commits. If anything fails, the job rolls back and the records in memory go back to their values at the start of the job, so a retry runs on the same data as the first time. Outside a job every change is written and committed at once, and debug mode warns about it.

EventDatabaseThen
done, stopwrite, committhe process continues
commit;write, commit, begin a new transactionthe job continues
rollback;rollback, memory restoredthe job ends with status "rolled back"; the process continues after done; recover does not run
an error in the jobrollback, memory restoredrecover runs
the connection is lostthe server rolls backa transient DatabaseError: a case for retry
power loss, killthe database rolls back; SQLite recovers its log at the next opennothing runs

Example: a dry run


# raise the prices of one category, with a dry run
driver reprice is
  class Product = {id: Integer, category: String, price: Decimal, version: Integer} <: Record is
    method validate(@self) is
      expect self.price > 0d;
    return;
  end Product;

  table products: Product in "shop" is
    key (id);
    version version;
  end products;

  process main(category: String, percent: Decimal, dry_run = False: Logic) is
    new changed := 0;

    reprice: job
      set $isolation = "repeatable read";
    do
      for p in products.where!("category = ?", category) do
        let p.price := (p.price * (100d + percent) / 100d).round(2);
        let changed += 1;
      done;
      print "{changed} products to change";
      rollback if dry_run;           ** nothing is written, the job ends rolled back
    done reprice;                    ** one update per product: set price, version

  recover
    if $error is ConflictError do
      retry after 1s if $error.attempt < 3;     ** read the products again
    else if $error is DeadlockError do
      retry after 2s if $error.attempt < 5;
    done;
    abort;
  return;
end reprice;

Isolation and locks

The isolation of a job is the default of the database: read committed for PostgreSQL and MySQL, serializable for SQLite. A job changes it in its declarations with system variables, in the way an aspect shadows $timeout:

VariableMeaning
$isolation"read committed", "repeatable read", "serializable", "snapshot"
$lock_timeouthow long a statement waits for a lock, for example 10s
$read_onlyTrue: a read-only transaction, one consistent snapshot, for reports

A deadlock or a serialization failure is a DeadlockError, a transient error. find!(key, lock: True) locks a row until the commit.

Optimistic locking

With a version clause every update and delete says and version = the version I read. If no row matches, someone else changed the row: the record becomes stale and the job fails with a ConflictError. The rollback detaches the records first read in the job, so a retry reads them fresh. Without version the last writer wins, and debug mode warns once per table that more than one job writes.

Long loads: commit and checkpoints

A job that loads ten million rows should not hold one transaction for an hour. commit; inside the loop commits each batch. But a retry runs the job again from its start, and would load the committed batches twice. The rule: a job with commit; keeps a checkpoint, written in the same transaction as the batch, and starts from it:


load: job
  new since := checkpoint.read!(:Instant)("orders", db: "sales", default: Instant.epoch);
do
  for batch in source.where!("created > ?", since).batch(10000) do
    for o in batch do
      let target <+ to_target(o);
    done;
    checkpoint.write("orders", batch[-1].created, db: "sales");
    commit;                          ** the batch and the checkpoint, together
  done;
done load;

db: "sales" keeps the checkpoint in the table eve_checkpoint of that database, so it commits with the batch. A load with upserts is also safe to repeat: the second load of a batch changes nothing.

Two databases in one job

A job may write to two connections. Eve commits them one after the other and does not use two-phase commit. If the second commit fails after the first succeeded, the job fails with a CommitError that has partial: True and the list committed. retry and resume are refused for it, because the job can not be undone. Prefer one target per job: stage in one job, move in the next.

Direct SQL

Everything that is not rows is SQL. These methods of a connection run in the transaction of the session and track nothing:

MethodResult
query!(:T)(sql, args)Stream(:T), columns matched by name
query!(sql, args)Stream(:DataMap)
query_one!(:T)(sql, args)T?
execute!(sql, args)the number of rows changed
script(path)runs a SQL file of the folder sql/, statement by statement
 

new sales := database.connect("sales");
for r in sales.query!(:Order)("select id, customer_id, amount, created from orders where amount > ?", 100d) do
  print "{r.id}: {r.amount}";
done;

Values are always parameters. A {...} placeholder of Eve inside the SQL text is a warning, because it can open the door to SQL injection. After a direct write, call refresh on the records you still use: Eve does not know which ones the statement changed.

Scripts, procedures and commands

  • Scripts. A SQL file of the project installs or changes a structure, disables indexes or prepares a bulk load: sales.script("create_orders.sql"). DDL goes through scripts and the command db migrate, never through the ORM;
  • Stored procedures. They are declared with external and run in the transaction of the job;
  • Commands. The databases of a machine are administered at the prompt: db list, db add, db remove, db test, db info, db tables, db describe, db sql, db script, db create, db create-table, db migrate, db backup, db prepare, db activate, db reindex, db cache. They run with the rights of the database user of the connection: Eve adds no layer of rights.

Introspection

The system variable $query holds the text of the last SQL statement of the process. In debug mode $trace prints every statement with its parameters (secrets are masked) and its duration.

Drivers and the Eve server

A driver is a Zig module that implements one interface: open, transactions, prepared statements, batches, bulk load, the catalog for the validation, the dialect and the classification of errors. The core, the ORM and the server never depend on a vendor. The order: SQLite (embedded) and PostgreSQL in version 0.4, with Supabase and Neon, which speak its protocol; MySQL and MariaDB, and Cloudflare D1 in 0.5; MongoDB later, with an API of its own; Oracle and SQL Server by the community, through the same interface.

On path 3 a desktop or an edge machine holds no password and does not reach the database network. The Eve server holds the sessions, the drivers and a cache:

  • A remote session has a lease, renewed while the client works; a client that crashed does not hold locks for long;
  • Each transaction has an id that the server writes in the same transaction as the data. After a broken connection the client asks the server whether that id is committed, so it knows if the job passed or must be retried;
  • Only the changed columns travel: an update of one field of a record of fifty fields sends one value, the key and the version;
  • cached 1h; keeps a reference table (countries, currencies) in the cache of the server. A write goes to the remote database first. The cache is never the authority: do not use a cached table for a decision that needs the current value;
  • A bulk ETL between two databases should run on the server, with a remote apply, so the rows do not cross the network twice.
