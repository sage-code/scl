Eve Concurrency

Eve does parallel work with methods. A method called by its name runs on the core of its caller. A method started in a parallel group runs on a worker core, so one process can use all the cores of the computer. Tasks exchange data through output parameters, at the barrier that closes the group, or through channels while they run. This chapter starts with methods and parameters, then explains parallel groups, the data rules, Bulk Synchronous Parallel, channels and how to choose a model.

Methods

Before we can run methods in parallel we must understand the concept of simple method. In Eve we create a subprogram that can receive parameters and can have side-effects. You can call a method by name, with or without arguments enumerated in a list. A method is created with keyword "method" and is ending with keyword "return". Method do not have to be follow by empty parenthesis when it has no arguments. A method can be declared in a class or at module level, outside any class. A module-level method is public when its name starts with a dot (method .name) and private when it starts with an underscore (method _name). A method can also return a result.

Syntax:


# define a method
method name(parameter_list) is
    ** method statements
    ...
return;

Example

Next example demonstrate two methods: "foo" and "bar". We declare the methods and then call the methods. One of method has no parameters, the other has 3 parameters. Two input and one output parameter.


# demonstrate two methods
driver process_demo is

  ** foo has no parameters
  method foo is
    print "I have no arguments";
  return;

  ** bar has 3 parameters
  method bar(param1:Integer, 
              param2 = 0: Integer,
              @result: Integer) is
    print "I have two parameters: param1 and param2";
    result := param1 + param2;                    
  return;

  process main is
    foo; ** call method without arguments
    let output:=0; ** prepare a variable to receive output

    ** execute method with 2 arguments and receiver
    bar(1, 2, @output);
    expect output == 3; ** the value of output should be 3.
    print ("output=", output);
  return;
end process_demo;

Side Effects

A process can use process states and can have side-effects. When a global state is changed by a method this is called side-effect. This may be useful but potential unsafe. Some side effects may be harder to debug. It is safer to use input/output parameters than side effects.

these are side effects...

  • modify a global variable or system state;
  • open and write into an external file;
  • print a message or accept input from console;
  • upload something on internet or network;

Examples

Next method: "add_numbers" has side effects:


driver side_effect is
  set test   :Integer;
  set p1, p2 :Integer;

  ** method with side effects
  method add_numbers is
    test := p1 + p2; ** first side-effect
    print test;          ** second side-effect
  return;

  ** define main process
  process main is
    p1 := 10;
    let p2 := 20;
    add_numbers; **  method call without arguments
    expect test == 30;
  return;
end side_effect;

Note: In Eve it is not required to use empty parenthesis() to call a method. Only functions require empty brackets. We will talk about functions later. This feature enable us to extend Eve using Eve scripts.

Parameters

Parameters  are defined in round brackets () separated by comma. Each parameter must have type and name. Parameters are optional. Eve offer a range of advanced features: optional arguments, default values, variable number of arguments and input/output arguments.

Parameter Syntax:

Mandatory parameters do not have initial values but only declared type. Optional parameters have initial value that is assign using operator "=" with explicit :type, or ":=" with type inference. Arguments can be pass by position or by name.

  • parameter :Type
  • parameter = value :Type
  • parameter := expression
  • @parameter :Type

A parameter without "@" receives its argument by value, also a collection: the method works on its own copy and the caller's variable does not change. A parameter with "@" is an input/output parameter: it receives a reference to the caller's variable, so the method reads its value and can change it. An "@" parameter can't have a default value, so it is never optional.

Notes:

  1. One method can receive one or more parameters,
  2. Parameters having initial values are optional,
  3. Values used for parameters at runtime, are called "arguments",
  4. You can assign arguments by position using a list of values,
  5. You can assign arguments by name using (name:value) pairs;

Vararg parameters

One method can receive multiple arguments of the same type into a single collection parameter. This can be a List, DataSet or HashMap, depending on declaration.

  • First arguments can be captured using named parameters,
  • The rest of arguments are captured into vararg parameter,
  • A method can have one single vararg parameter,
  • The vararg parameter name is declared using prefix: "*",
  • You can use any name but "*args" is the usual name for it.
Note: Also the main process of a driver or aspect can receive parameters. The same convention apply for aspects, drivers, functions and methods. Eve offer same features for all subprograms. The only difference are the call concentions.

Example:

Next driver can have a list of arguments. The arguments have no names, so it will just print all the arguments it has received. Drivers receive argument values from command line or REPL console using "run" command.

# print all arguments
driver test is

  ** list all arguments
  process main(*args: ()String) is
    loop
      let arg :String;
    for arg in args do
      print arg;  ** expect 1,2,3
    done;
  return;
end test;


eve:>run test.eve 1 2 3

Output Parameters

To avoid overuse of global variables you must use input/output parameters. We prefix output parameters using symbol "@", and the caller writes "@" before the argument too: add(1, 2, @result), or by name add(1, 2, op: @result). The "@" asks for pass by reference; without it the argument is passed by value. An output argument must be a variable, an element or a slice, otherwise you will not be able to capture the output value. The compiler will complain if you do not send a valid reference to an output parameter.


#demo output parameters
driver output_params is

  ** private method
  method add(p1 = 0, p2 = 1: Integer, @op: Integer) is
    op := p1 + p2;
  return;

  process main is
    let result: Integer;

    ** input/output argument requires a reference to a variable
    add(1, 2, op: @result);
    print result;  ** expected value 3

    ** negative tests, will fail
    add(1, 2, result); ** error, "op" requires @
    add(1, 2, @4);     ** error, "op" requires a variable
  return;
end output_params;

Notes:

  • Output parameters are usually the last parameters;
  • Output parameters are having "@" prefix, and so are their arguments;
  • An output parameter has no default value;
  • Method invocation is done using name of method as a statement;

Parallel model

Not in Eve 0.1. Parallel groups and channels are designed but not implemented in version 1; their keywords are reserved. In version 1 a process runs on one core, and a method always runs to completion on the core of its caller.

Eve does parallel work with methods. An aspect is never run in parallel: apply aspect.process(args); runs a process in serial mode and the caller waits for it. Inside a process, the work can span all the cores of the computer. These are the concepts:

  • Process: the master. It runs on one core and opens the parallel groups, one after the other;
  • Parallel group: a block parallel … do … done that starts methods and waits for all of them;
  • Task: one method started with start. It runs on a worker core with its own copy of the input arguments;
  • Barrier: the closing done. The process waits there until every task of the group has returned; then the outputs (@) are ready;
  • Channel: a queue that connects tasks running at the same time. A task sends values into it, another task receives them.

With these elements Eve supports three models of parallel work: task groups (different methods side by side), Bulk Synchronous Parallel (the same method on slices of the data, in supersteps) and pipelines (stages connected by channels). A method called by its name, without start, is not parallel: it runs on the core of its caller and returns when it has finished.

Parallel groups

A parallel group starts methods that run at the same time. The process executes the groups one by one: a group begins after the previous group has finished. Each group can have an optional name.

Syntax:


[name:] parallel
  ** declarations, local to the group
do
  start method_name(arguments);
  ...
done [name];

parallel … do … start … done

Example: task group


# parallel groups demo
driver parallel_demo is

  ** work done by one worker
  method task(n: Integer) is
    print ("task ", n, " is running");
  return;

  process main is
    ** main process is a series of sequential groups

    group1: parallel
      ** local variables for group1
    do
      start task(1);
      start task(2);
    done group1;

    ** group1 is now complete, group2 starts

    group2: parallel
      ** local variables for group2
    do
      start task(3);
      start task(4);
    done group2;

    ** Both groups are now complete
  return;
end parallel_demo;

Notes:

  • Each group executes sequentially. Within a group, the started methods run concurrently, on several cores;
  • start is allowed only in the do region of a parallel group, and it starts only methods. start aspect.process() is an error: use apply;
  • The do region can use control statements, for example a loop that starts the same method several times;
  • The closing done waits for all the methods started in the group, and it is always for a single group;
  • The label of a group is optional. A group without a label starts with parallel and ends with a naked done;; a labeled group ends with done label;.

One process can start the same method several times with different arguments, to compute different parts of the data. Every started method writes its own element of the array s: two started methods never receive the same output variable.


## create parallel work
driver parallel_loop is

  ** compute one result
  method square(n: Integer, @result: Integer) is
    result := n * n;
  return;

  process main is
    let s: [4]Integer; ** one result for each worker

    ** start the same method 4 times
    demo: parallel
    do
      for i in (1..4) do
        start square(i, @s[i]); ** runs in parallel
      done;
    done demo;
    ** all started methods have finished, s is ready
    print s; ** [1,4,9,16]
  return;
end parallel_loop;

Data rules

Tasks run at the same instant, so two tasks must never write the same data. Eve guarantees this with a few rules; it needs no locks and no shared mutable objects, except channels.

  • Inputs by value: the arguments are evaluated at start. An argument without "@" is passed by value, also a collection: the task works on its own copy, and the process can go on changing its variables. The virtual machine shares a large collection and copies it only when one side writes into it (copy on write), so passing by value is cheap;
  • One owner for each output: an output argument (@) is passed by reference and belongs to one task. Two tasks of the same group can't receive the same variable, the same element or two overlapping slices as output. The compiler rejects what it can prove; the virtual machine checks the rest at start and raises an error;
  • Channels are the exception: a channel is the only object that several tasks of a group can receive with "@". It is built for that: its operations are safe when tasks use it at the same time;
  • No globals: a started method can't change the globals of the driver. It can call other methods by name; they run on the same worker. It can print, but the lines of different tasks come in any order;
  • No nesting: a started method can't contain a parallel group.

Errors and time-out

  • When a task raises an error, the tasks of the group that have not begun are cancelled, the running ones finish, and done raises the first error in the process. The next groups do not begin, so a recover region of the process can catch the errors of all the started methods;
  • A task that waits on a channel longer than $timeout (60 seconds by default, set in the configuration file of the driver) raises a time-out error;
  • When every unfinished task of a group waits on a channel, nothing can move any more: this is a deadlock. The virtual machine detects it and raises a deadlock error at done.

Workers

The number of started methods is not limited by the number of cores. The virtual machine keeps a pool of worker threads, one for each core, and queues the extra tasks. The pool size is the system variable $cores: by default the number of hardware cores, it can be set in the configuration file of the driver. A task that waits on a channel gives its core to another task, so a pipeline with more stages than cores still works.

The number of tasks can be dynamic. You can read it from the configuration file, compute it from the size of the data or from $cores, or hard code it as a constant inside the driver. This gives you flexibility to tune your process.

Bulk Synchronous Parallel

The recommended pattern for parallel work is Bulk Synchronous Parallel (BSP). The computation is a sequence of supersteps. A superstep has three phases:

  1. Compute: every worker computes on its own part of the data, without talking to the others;
  2. Communicate: every worker writes its results into its own output;
  3. Synchronize: a barrier waits for all the workers. After the barrier, all the results are visible.

In Eve, one parallel block is one superstep, and its done is the barrier. Between two blocks the process runs alone: it combines the partial results or prepares the data for the next superstep. An iterative algorithm puts the parallel block in a loop.

Example: parallel sum

Next driver computes the sum of 32,000 random numbers with 32 workers. The data is split into 32 slices, one for each worker, and every worker writes one element of the array partials.


# parallel sum with one BSP superstep
driver parallel_sum is
  set workers = 32 :Integer;
  set size = 1000 :Integer; ** elements for one worker

  ** local computation: one slice in, one partial sum out
  method partial_sum(data: []Integer, @partial: Integer) is
    partial := 0;
    for x in data do
      partial += x;
    done;
  return;

  process main is
    let data: [workers * size]Integer;
    let partials: [workers]Integer;

    ** produce the data
    for i in (1..workers * size) do
      data[i] := (0..99).random();
    done;

    ** superstep: 32 workers, one slice each
    sums: parallel
      let first: Integer;
    do
      for w in (1..workers) do
        first := (w - 1) * size + 1;
        start partial_sum(data[first..first + size - 1], @partials[w]);
      done;
    done sums; ** barrier: all the partial sums are ready

    ** combine on the main core
    let total := 0;
    for p in partials do
      total += p;
    done;
    print total;
  return;
end parallel_sum;

The same job can be written as a pipeline, with a producer, 32 consumers and channels between them (see Channels). For data that is already in memory, the BSP version is simpler and safer:

  • no shared object: every worker reads its own slice and writes its own element;
  • no blocking: a worker never waits for another worker, only the process waits, at done. There is no buffer that can fill up, so there is no deadlock;
  • deterministic: the partial results are combined in index order, so the result is the same on every run, also for floating point numbers, where the order of a sum changes the rounding;
  • one error point: errors arrive at the barrier, where the recover region of the process can handle them;
  • predictable cost: a superstep lasts as long as its slowest worker, plus the barrier.

Example: iterative supersteps

Next driver simulates the heat that flows along a bar. The bar is an array of 1002 cells. The first cell is hot and the last cell is cold; they don't change. At every step, a cell takes the average of itself and its two neighbors. The 1000 inner cells are split into 10 slices. A worker receives the current state cur by value and writes its slice of the next state nxt by reference. After the barrier the process clones nxt into cur with ::; an assignment := would share the array instead of copying it, and the next superstep would read and write the same cells. This copy is the communication between supersteps: in the next superstep every worker sees the new values of its neighbor slices.


# heat diffusion with iterative BSP supersteps
driver heat_bar is
  set workers = 10 :Integer;
  set width = 100 :Integer; ** cells for one worker

  ** compute one slice of the next state
  method smooth(cur: []Real, first: Integer, @part: []Real) is
    for k in (1..part.count()) do
      let i := first + k - 1;
      part[k] := (cur[i - 1] + cur[i] + cur[i + 1]) / 3;
    done;
  return;

  process main is
    let cur: [workers * width + 2]Real;
    let nxt: [workers * width + 2]Real;
    cur[1] := 100.0; ** hot end, the cold end stays 0
    nxt[1] := 100.0;

    for n in (1..500) do
      ** compute in parallel
      superstep: parallel
        let first: Integer;
      do
        for w in (1..workers) do
          first := (w - 1) * width + 2;
          start smooth(cur, first, @nxt[first..first + width - 1]);
        done;
      done superstep; ** barrier

      ** communicate: the next state becomes the current state
      cur :: nxt; ** clone: cur is a new copy of nxt
    done;
    print cur[2..11]; ** temperature near the hot end
  return;
end heat_bar;

Channels

A channel is a queue with a fixed capacity that connects tasks running in the same group. A producer task sends values into the channel; a consumer task receives them in the same order. When the channel is full, the sender waits; when it is empty, the receiver waits. In this way a fast stage can't run away from a slow one, and data flows through the tasks while it is produced. This is the right tool for streams: data that arrives over time or does not fit in memory.

Create a channel

Channel(:T) is a generic class of the core library. The type parameter is the type of the values; the constructor takes the capacity and, optionally, the number of senders.


  let jobs := new Channel(:Integer)(capacity: 100);
  let results := new Channel(:Real)(capacity: 100, senders: 4);

Operations

OperationMeaning
ch.send(value);put a value at the end of the channel; wait while the channel is full. Sending into a closed channel is an error
for x in ch do … done;receive the values one by one, waiting for each; the loop ends when the channel is closed and empty
ch.receive(@x);receive one value into x; wait while the channel is empty. Receiving from a closed, empty channel is an error
ch.close();a sender has finished. With senders: n the channel closes after the n-th close; without it, after the first
ch.count()the number of values waiting in the channel, for monitoring

Rules:

  • A channel is created by the process, before the group or in the declarations of the group, and it is passed to the tasks with "@": start produce(@jobs);. The parameter is declared @jobs: Channel(:Integer);
  • Every sender must close the channel when it has finished, otherwise its receivers wait forever (until the time-out). With several senders, create the channel with senders: n, so the receivers stop after the last sender;
  • Values sent into a channel are copied, like arguments passed by value: a receiver never shares data with the sender;
  • The order of the values from one sender is kept. With several senders the values are interleaved in any order, so a result that depends on the order is not deterministic;
  • After done all the tasks have finished. The process can still read what is left in a closed channel with for x in ch do, but it is better to collect the results inside the group, as below.

Example: pipeline

Next driver has three stages. One producer sends 10,000 random numbers into jobs. Four workers receive from jobs, square every number and send it into results. One collector receives from results and adds the values into total. The three stages run at the same time, and the barrier done flow waits for all six tasks.

produce → jobs → square ×4 → results → collect


# pipeline: producer, 4 workers and a collector
driver pipeline is
  set workers = 4 :Integer;

  ** stage 1: produce the numbers
  method produce(count: Integer, @jobs: Channel(:Integer)) is
    for i in (1..count) do
      jobs.send((0..99).random()); ** waits while jobs is full
    done;
    jobs.close(); ** no more numbers
  return;

  ** stage 2: square every number
  method square(@jobs, @results: Channel(:Integer)) is
    for x in jobs do ** ends when jobs is closed and empty
      results.send(x * x);
    done;
    results.close(); ** one of the 4 senders has finished
  return;

  ** stage 3: collect the results
  method collect(@results: Channel(:Integer), @total: Integer) is
    total := 0;
    for y in results do ** ends after the 4th close
      total += y;
    done;
  return;

  process main is
    let total: Integer;
    let jobs := new Channel(:Integer)(capacity: 100);
    let results := new Channel(:Integer)(capacity: 100, senders: workers);

    flow: parallel
    do
      start produce(10000, @jobs);
      for w in (1..workers) do
        start square(@jobs, @results);
      done;
      start collect(@results, @total);
    done flow; ** barrier: all the stages have finished

    print total;
  return;
end pipeline;

Notes:

  • The capacity limits the memory: at most 100 numbers wait in each channel, whatever the size of the stream;
  • The collector runs inside the group. If the process tried to read results after done, the workers would wait on a full channel and the group would never end: the virtual machine would report a deadlock;
  • Only the collector writes total, so the output rule (one owner) holds;
  • A sum does not depend on the order of the values. For results that do, send an index with each value, or use BSP.

Choosing a model

ModelShapeShared dataResultUse it for
Task groupdifferent methods side by side, one barriernone: inputs by value, one owner for each outputdeterministicindependent jobs: read several files, call several services, build several reports
Bulk Synchronous Parallelthe same method on slices of the data, a barrier after each superstepnone; data is exchanged by the process between superstepsdeterministicdata in memory: aggregations, arrays and matrices, iterative algorithms
Pipelinestages connected by channels, running at the same timechannels onlyorder not guaranteed with several sendersstreams: data that arrives over time or does not fit in memory, input and output overlapped with computing

Start with a task group or BSP: a worker never waits for another worker, so they can't deadlock and they give the same result on every run. Use channels when the data is a stream. A process can combine the models: for example a pipeline that reads a large file in one group, then BSP supersteps on the data it has collected.
