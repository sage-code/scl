Eve Topology

Eve is designed to quickly build a data processing app that can have jobs to be executed in order on a precise schedule. You can create one module app but sometimes you need to divide a project into many small modules that run together. Eve provide features to do both kinds of applications.

Projects

A project is a folder with a specific structure. It contains one or more applications that can run independent of each other on the same computer or a group of computers.

project structure

Next project contains two applications: server/agent and show folders where you should put your code (src+lib) and documentation (doc). This is a recommendation but not a hard rule.

$pro_home
project

  |   |-- aspect2.eve

Scripts

Eve define several kind of scripts that together makes a "project suite". Some scripts are reusable but some are specific to a single project. Here are all the possible scripts:

  • Driver, created with keyword: "driver",
  • Aspect, created with keyword: "aspect",
  • Module, created with keyword: "module",

Notes: One project can contain one or many drivers. Each driver is an independent script. A driver has a single executable process. A driver control the execution of aspects. An aspect is encapsulated and contains its own process. An aspect can receive parameters from the driver. An aspect or driver can "import" modules and can use classes or functions defined in these modules.

Features:

  • A driver can import one or more modules;
  • A driver can apply aspects in a sequence or start them in parallel;
  • A driver or aspect define a single executable process;
  • An aspect or driver can import modules;
  • Only a driver defines global states; every driver has its own global scope;
  • Aspects and modules define public and private members, used with the dot operator.

Regions

A script file is divided into regions using keywords: {import, alias, constant, global, process, initialize}. Indentation is mandatory: the members of a region are indented by exactly 2 spaces, and the compiler reports an error when the indentation is wrong. A region ends when the next region begins. Region keywords are left-aligned (they start at column 0). A class is not a region: each class is declared on one line, class Name = {...} <: Type;. The regions differ by kind of script: the canonical skeleton of a driver is below, of an aspect in Aspects and of a module in Modules.

Driver skeleton:

An Eve script begins with one of these keywords: {"driver", "aspect", "module"}. Script name is the same as the file name without the extension. A driver or aspect script can have parameters, defined after script name in a list, but a module do not have parameters.


** purpose of the driver
driver driver_name is

** system variables and constants: right after the header, 2 spaces
  set $sys_con = value;
  set LIMIT = 10 :Integer;

** import region
import
  from $path/library_name use (*);

** qualifier suppression region
alias
  def AliasName = library_name.MemberName;

** constant region: a visual delimiter for constants
constant
  set NAME = Value :Type;

** global region: classes, functions, global variables
global
  class Person = {name:String, age:Integer} <: Object;
  set expression_name = (params) => (expression);
  let shared = value1 :user_type;

** main process
process main is
  let my_var = value :Type;  ** private to the process
  ** executable region
  ...
recover
  ** error handling area: retry, resume or abort
  ...
finalize
  ** release locked resources, consume the job report
  ...
return;
end driver_name;

Members

  • a script can define members, visible in process;
  • a script can import public members from modules;
  • a driver can "set" system variables and constants using "$" sigil;

Note: The constant region is a visual delimiter for constants. You can also ignore the constant and global regions and write declarations directly under the script header, indented by 2 spaces. They belong to the global scope, which is bound to the process scope.

Note: Only a driver defines global states. In its global scope you can set constants and system variables, and define global variables, classes, functions and methods. Aspects and modules define public and private members instead (see Module Import).

The keyword "set" creates a constant; the keyword "let" creates a variable. You can not define global variables in the constant region. Global constants and variables are static: they are created on the heap and have a permanent nature.

System Variables

System variables use prefix "$". These are defined and maintained by EVE virtual engine. Values for these variables can be read automatically by EVE engine at startup. Can be loaded from a configuration file (*.cfg). New variables can be defined by user for each script.

New system variables can be defined with the keyword set directly after the script header (or after the #! line), with 2-space indentation. No need to use global keyword for this unnamed first region: it is the global region. These are constants that belong to the global scope, the same scope used by the driver.

Note:

  • System variables can be defined in a configuration file,
  • OS environment variables are visible as system variables: the variable NAME is read as $NAME,
  • System variables are usually defined in core EVE modules,
  • System variables can be defined or overwritten in program modules,

Examples:

Several system variables are provided by Eve environment:

  • $EVE_DIR :eve runtime
  • $EVE_LIB :eve lib folder
  • $MY_DIR :program location
  • $MY_LIB :project lib folder
  • $MY_LOG :project log folder
  • $OS_PWD :current working folder

System objects are instantiated at startup and are part of core library. These contain runtime information that you can use for debugging. System objects do not need module qualifier. You can access them directly once the module is imported.

  • $error :contains last error with code & message
  • $stack :contains debug information about current call stack
  • $trace :contains reporting information about executed statements

Global Constants

The name of a constant is not enforced by the compiler; the tutorial only recommends it. By convention, constants use capital letters, and the next symbols in a constant name can be numbers or underscore but no special or Unicode character.

Example


** define global scope
constant
  set PI  = 3.14 :Real;       ** global constant
  ...
global
  let var = 0    :Integer;    ** global variable
  ...

Notes:

  • You can create new global constants and variables;
  • Prefix "$" for system constants to avoid scope qualifier;
  • OS environment variables are visible as $NAME;
  • System constants are capitalized and also begin with "$";

Example


driver test is

** driver context constant
constant
  set E = 2.718281828 :Real;    ** Euler's number

** driver context: class and variable
global
  class Person = {name:String, age:Integer} <: Object;
  let x = 0 :Integer;           ** global state
  ...

Notes:

  • Global constants are created using keyword "set", global variables using keyword "let",
  • All global states are bound to the process scope,
  • We are using operator "=" for initialization,
  • Operator ":=" executes an expression and can be used in any region, including the global regions, for example a string concatenation,
  • Constants are by convention using uppercase letters, the compiler does not check it,
  • $user_path is a shared variable defined by the user;
  • spaces in script-names are not supported you must use: "_";
  • aliases are created with "def" from public members of other modules;
  • a path is a string, built with the smart concatenation operator /

Import Region

The import is used to include public members from modules:

Syntax:


driver script_name is
  ** define global system variable
  set $user_path := root_path/relative_path;

import
  from $user_path use (module_name,...);  ** specific modules
  from $user_path use (*);                ** find all modules
  ...
alias
  ** create alias for some of the hidden members
  def new_name = module_name.member_name;
process main is
  ...
return;
end script_name;

Notes:

  • A path is a string. The operator / is a "smart concatenation": between strings it joins path segments and it becomes \ on Windows;
  • An alias is created with "def Name = library_name.MemberName;". An alias of a parameterized class, like ClassName[parameters], is not supported;

Process

A process is a named executable region of a script, mandatory for drivers and aspects. It is declared process name is … return;, and the driver or aspect itself closes with end script_name;. The entry point is the process named main. A script can declare other processes, started with start name(args); (the caller waits) or, inside a parallel block, with begin name(args);. Running an aspect creates its main process, which can start further processes.

A process can receive parameters, input and output (process name(n: Integer, @total: Integer) is). A process returns no result: its outputs are the parameters marked with "@". The arguments are passed in a list, start total(10, @sum);, and the same list is used by "begin" in a parallel block. With "start" the caller waits, so the outputs are ready on the next statement. With "begin" the process runs in parallel, so an output is ready only after the "join" of its group. A process reads and changes the global members of its script: the module globals when it is declared in a module, the driver globals when it is declared in a driver.

While modules don't use the 'process' keyword, they have an initialization region that serves a similar purpose. This initialization region is executed first when a process starts. For modules imported by a driver, the initialization runs within the driver's main process. When imported by an aspect, it runs in the sub-process created by that aspect.

Process context

Every process has a local context. In this context you can define variables, and instantiate objects but you can't define classes, methods or functions. Process local members can't be shared but can be send as input/output parameters to subprograms or aspects.

Process Termination

Process can be early terminated using: "over" or "panic". This is a way to release all locked resources and terminate the process. The statement "over" ends the process it is in with code 0. The statement "panic" is an unhandled exception: it ends the whole application with code 1, not only the process; "panic 0" is not allowed and there is no "panic N". A failed "expect" always ends with code 2, and "raise" ends with an error code greater than 0.

Example:

Next code sequence is terminated after 11 iterations:


# terminate a program with: over
driver test_over is

process main is
  loop
    let i = 0 :Integer;
  while True do
    write "."; wait  10;
    over if i > 10;
    i += 1;
  done;
return;
end test_over;

Drivers

A driver represents the application main script. It has the role to lead the application main process. When driver execution is over the application give control back to the EVE virtual machine. If no other process is running, the machine shuts-down after it clean-up the memory.

Notes:

  • Any application can have one or more drivers,
  • A driver is the process entry point,
  • A driver can read configuration files at startup,
  • A driver can receive parameters;
  • A driver has one process named main, and can declare other named processes;
  • A driver is independent, can not be imported;
  • A driver is the only script that defines global states;

Aspects

An "aspect" is a script specific to a particular project. It resolve a problem or address a specific concern. Aspect files are executable. One aspect can execute other aspects, however it can't be recursive.

An aspect can receive parameters. One aspect has a declaration region and a mandatory process. The driver executes the process of an aspect with the keyword "apply". An aspect must handle its own errors, it can't raise errors. If errors are not handled, the program panic and stop execution.

Aspect skeleton:


** purpose of the aspect
aspect aspect_name(parameter_list) is

** public and private members: an aspect defines no globals
  let .result = 0 :Integer;  ** public member, prefix "."
  let count = 0 :Integer;    ** private member

import
  from $path/library_name use (*);

process main is
  ** executable region, mandatory
  ...
recover
  ** handle all errors
  ...
finalize
  ** release locked resources
  ...
return;
end aspect_name;

Running an Aspect

Aspect is executed with keyword "apply". An aspect can be executed synchronously (apply) or asynchronously (with "begin" in a parallel block). Both create the main process of the aspect. We will explain more about aspect execution after we define the control flow, asynchronous methods, functions and error handling. At this time let's focus on Driver execution and Modules.

Modules

A module is one script file with the extension ".eve" and the header module name is. Modules can be combined together in large projects. Some modules are common for many projects. These are called system modules or library modules. A folder of modules is a library. The term "crate" is not used in Eve.

modules ...

  • are one script file each, stored in a library folder,
  • can use each other,
  • belong to one or more projects,
  • can define public or private members,
  • have no process: they can be imported but not applied,
  • can be initialized when imported first time

Module skeleton:

An Eve module begins with "module" keyword. Module name is the same as the file name without the extension. A module can have an initialization region. This is executed when the module is imported for the first time. That is the difference, a module do not have a "main process".


** purpose of the module
module module_name is

** public and private members: a module defines no globals
  let .counter = 0 :Integer;  ** public member, prefix "."
  let total = 0 :Integer;     ** private member
  ...

import
  from $path/library_name use (*);

initialize
  ** setup initial states, executed when the module is first imported
  let counter := 0;
  ...
finalize
  ** verify states & log
  $error.log();
  ...
end module_name;

Notes:

  • Modules are not executable and can't define processes;
  • Modules can define public and private members;
  • Modules are loaded in a process that belong to driver or aspect;
  • A module "initialize" region is executed immediate after module is loaded;

Module names are using lowercase letters, can contain underscore or digits but no special characters and no Unicode strings. Longer names that use several words can be separated with underscore. The module name can be 30 characters long.

Module files: A module is a single script file. A library is a folder that contains many module script files. In the import statement you can name the modules one by one, or you can name the library folder and concatenate it with the module name using the smart concatenation operator "/".

Configuration

EVE virtual machine can load system environment variables from a configuration file. These are stored as "$key = value" pairs, where the value is a valid Eve literal. Some system constants can be derived from environment variables using the smart concatenation operator "/".

A configuration file have extension .cfg. One application can run with different configuration file. Application documentation must contain description of all variables required by the application.

A good practice is to provide a configuration template . The template file may contain # comments and $key = value pairs. Values can be numeric, string, symbol, date, time or data literals: [],(),{}. Eve application will automatically parse configuration file to read values for the system variables.

Library

A library is a set of reusable modules. A library can be installed in EVE environment or can be project specific. EVE machine is using a special system variable to search for a library: $EVE_LIB. If the library is not found the module can't be imported and the script fails.

  • libraries contain generic functionality and can be shared between multiple projects;
  • using import, several modules can be loaded from a library one by one or all using (*);
  • circular import is possible, but EVE prevent infinite recursive reference;
  • after import you can call public members of a module using dot notation;

Note: A library is a folder of module script files. A module is one script file and its name is the file name without the extension. By convention you can create intermediate subfolders but only the last folder is the library and module names must be unique in a library.

Script Execution

Planned, not in 0.1: VM parameters, service mode, console REPL and exclusive mode are planned for a later version (about 0.9). Eve 0.1 only runs a script: eve script.eve.

Eve scripts are executed using a virtual machine. You can start the virtual machine as a service or as console application. In console you can run only one driver script at a time. In service mode you can run multiple drivers in parallel. Each driver is independent, it has its own scope (memory location) and can't communicate with other drivers executed by EVE in the same time.

Configuration:  Eve services using a general configuration file: eve.cfg. This file contains default settings for EVE machine. System variables are shared. A copy of EVE system variables is send to every new driver instance.

Configuration settings are loaded over the default values and have priority. In a process, you can temporary change the settings with an assignment. These changes do not propagate back into the configuration file.

Memory allocation: EVE service is in charge of allocating memory for each process. There is no shared memory between processes. When a process is terminated the memory is cleaned up of garbage and the machine continue to run until all processes are finished.

To execute a driver there are these ways:

  1. Using the "eve" system command: eve script.eve,
  2. Planned: using console REPL commands: parse, debug and execute,
  3. Planned: EVE virtual machine can be run as a daemon,
  4. Planned: you can control EVE virtual machine using command: eve with parameters

Driver Execution

When a driver is executed, all its components are compiled in memory, then the main process is executed. An aspect has its own process, run when the driver applies it; it can also be loaded from EVE console to call one process or function at a time, for testing purpose.

Start EVE REPL

EVE is a REPL machine. (Read Execute Print Loop). This machine has a menu and a command line. You can issue commands that can parse, debug and execute a script. This machine is planned and not yet created. It should work using "eve" command in console on Linux, Windows or Mac.

~/eve -c file.cfg

Operations

The machine has three operations on a script: parse, debug and execute. You can specify how much memory to allocate to the process with the option -m.

eve:> parse ~/path/driver_name.eve
eve:> debug ~/path/driver_name.eve -c file.cfg
eve:> execute ~/path/driver_name.eve -c file.cfg -m 2048GB

Eve REPL can be used to parse, debug or execute a driver step by step, using special commands. The command options are not yet fully designed. We will implement these basic commands:

command description
parse check the syntax and compile a script in memory, do not execute it
debug execute the main process in debug mode
execute execute the main process in production mode
begin start the driver main process step by step execution
enter this is actually the enter key. execute next step
print display value for a global variable, it can't print locals
resume continue running until a "halt" statement is encountered
report create a debugging report about system state
stop stop the driver execution but do not clean memory
clear stop the driver and clean the memory
setup load configuration file and set "$" variables
quit stop EVE machine and exit from REPL

You can use "halt" inside the script to stop a script and debug the script later. "halt" is working only when debug mode is active. Statement "halt" can be conditioned with "if" to create a debugging break-point. You should remove "halt" statements when the software is mature and do no longer need debugging.

In debug mode you can modify the configuration and reload using "setup" command. REPL must be in "ready" state when you reload settings otherwise you will get an error.

Module Import

The driver or aspect can import modules. After import, all public elements of modules can be used on demand. The parent process is controlling the execution. Remember, modules are not directly executable and must be hosted into a process.

Modules are "singleton" once a module is loaded in memory, it will bind its scope to the process. Only a driver defines globals. Aspects and modules define public members (declared with the prefix ".") and private members. A public member is used with the dot operator through the module name or an alias: alias.member. Two modules can define the same member name without conflict, because each one is reached through its own name or alias. Eve is a multi-session system. In each session you can run a single driver.

Exclusive Mode

Planned, not in 0.1. When eve is executed, it can be started with parameter: -x or --exclusive. This is a signal that only one session can run at a time. In this mode a second driver is refused while any other driver is active. Asynchronous methods started with "start" inside a driver are not affected. You can use this more especially for debugging or tuning purpose.
