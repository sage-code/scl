Eve Processing

Data processing is an important use case of Eve. A process can modify states, initialize variables, add/modify or remove data in collections, make computations and decision statements to resolve problems. Next we analyse some use cases:

Process Structure

A process can do one or more jobs. Jobs are sequential. A job has no error handlers: it passes or it fails. When an error is raised, in a job or anywhere else in the process, the process is interrupted and the workflow jumps into the recover region.

In the recover region you use normal control statements on the $error variable to decide what to do: retry the failed job, resume the process after it, or abort the process. Then the finalize region runs. An aborted error propagates to the calling process.

Jobs can be dependent. If the first job fails, it may not make sense to continue with the next job. In the recover region, $error.job is the label of the job that failed, so you can handle errors differently for each job or group of jobs.

job ... recover

Pattern:

Next design pattern show how to create several jobs in a process. Having a process with jobs will enhance your ability to crate robust code that can handle errors and prevent catastrophic defects.


# define process with jobs
process main is
  ** local declarations
  let tries := 0;
  ...
  ** preconditions: end the process prematurely
  ** over skips the recover and finalize regions
  panic if condition;

  ** description of c1 job
  c1: job
  do
    ...
  done c1;

  ** description of c2 job
  c2: job
  do
    ...
  done c2;

  ** description of c3 job
  c3: job
  do
    ...
  done c3;

  ** other statements after jobs are succesfully executed
  ** post condition checks for the entire process
  expect condition, "error message";
  ....

recover
  ** decide what to do next in case of error
  if $error.job == "c1" and tries < 3 do
    tries := tries + 1;
    retry;  ** run job c1 again
  else if $error.job == "c2" do
    print $error.message;
    resume; ** c2 failed, continue with c3
  else
    abort;  ** end the process with this error
  done;
finalize
    ** close resources or channels
    ...
    ** print debug messages
    ...
    ** report the errors (or not)
    ...
return;

Notes:For this design pattern we have demonstrate a sequential process that is more likely used by an aspect. We think this process structure provides a robust framework for error handling and flow control. It allows for:

  • Simple jobs, written so that they do not fail
  • Error handling in one place: the recover region decides per job
  • Guaranteed execution of cleanup code
  • Clear separation of concerns between different jobs in the process

Process Keywords

Notes

  • Any driver or aspect, can and must implement one single process;
  • A process create a local scope, but also has access to a global context;
  • Before first job there is a region for preparation/preconditions
  • Preconditions can end the process with over, which skips the recover and finalize regions
  • Jobs can't be nested, they are all on same level with the process
  • All jobs of a single process are execute sequential from top down;
  • When the project finish the local variables are released from memory;
  • You can create local variables, lambda expressions and new objects;
  • You can't define local functions, classes or methods in processes;

Aspect execution

An aspect is executed using the "apply" command. The call is explicit: it names the aspect and one of its processes, aspect_name.process_name(arguments), followed by the list of arguments. The parentheses are always written, also when there is no argument. An aspect has no main process: it hosts one or more named processes, and each call starts a process in its own scope.

Examples:

#these are all valid process calls
apply aspect_name.process_name();                          ** call process without arguments
apply aspect_name.process_name(argument_value);            ** call with single argument
apply aspect_name.process_name(value, value, ...);         ** call with a list of arguments
apply aspect_name.process_name(param:value,...);           ** call with a argument by name
apply aspect_name.process_name(value, value, param:value); ** mix position with names
apply aspect_name.process_name(value, *list_args);         ** use spreading operator
apply aspect_name.process_name(param:value, *map_args);    ** mix names with hashmap

Process interruption

A process normal ends with keyword return. When aspect process is terminated, program execution will continue with the next statement in the main process. Interruption keywords (exit, over, panic) can be used to interrupt a process. The exit or raise trigger the finalization region while "over" and "panic" skip the finalization region.

Example:


# simple aspect with one parameter
aspect print_this is
  process show(p:String) is
    print p;
  return;
end print_this;

# main process with parameters
driver process_call is
  process main(*args ()String) is
    ** number of arguments received:
    loop
      let arg: String;
    for arg in args do
      apply print_this.show(arg);
    done;
  return;
end process_call;

Aspect Execution:

One aspect is executed from a driver. You can not execute an aspect from itself. Recursive aspects are not supported. The compiler will detect a recursive aspect and will fail at runtime.

Aspects can be executed in serial mode one after another. Let's consider we have 3 aspects: {one, two, three}. Main process can execute each aspect using keyword: "apply" and can block the main process waiting for each aspect to finish. This will interrupt the driver main process and will execute aspect process one by one:


driver test_apply is

  # synchronous call
  process main is
    ** apply each aspect
    apply [folder/]aspect_one.run(arguments);
    apply [folder/]aspect_two.run(arguments);
    apply [folder/]aspect_three.run(arguments);
    ...
  return;
end test_apply;

Note: You do not have to import an aspect into a driver but you must specify the relative path of the aspect. If the aspect is in a subfolder, you must include relative folder name. If the aspect is in the same location as the driver, you do not need a folder name.

Parallel execution

Aspects are executed in serial mode: apply runs one process of an aspect and the caller waits for it to finish. An aspect process is never started in parallel. Parallel work happens inside a process: one process can span several processor cores by starting methods in a parallel block. Each started method runs on a worker core, and the process waits for all of them at the end of the block. The details, the data rules and the recommended pattern are in Concurrency: Parallel methods.

Parallel System

A parallel block groups methods that run at the same time. The process executes the groups one by one: a group begins after the previous group has finished. Each group can have an optional name.


# parallel groups demo
driver parallel_demo is

  ** work done by one worker
  method task(n: Integer) is
    print ("task ", n, " is running");
  return;

  process main is
    ** main process is a series of sequential groups

    group1: parallel
      ** local variables for group1
    do
      start task(1);
      start task(2);
    done group1;

    ** group1 is now complete, group2 starts

    group2: parallel
      ** local variables for group2
    do
      start task(3);
      start task(4);
    done group2;

    ** Both groups are now complete
  return;
end parallel_demo;

Notes:

  • Each group executes sequentially.
  • Within each group, the started methods run concurrently, on several cores.
  • start is allowed only in the do region of a parallel block, and it starts only methods. start aspect.process() is an error: use apply;
  • The closing done waits for all the methods started in the group, and it is always for a single group;
  • The label of a group is optional. A group without a label starts with parallel and ends with a naked done;; a labeled group ends with done label;;
  • Recover and finalize regions are optional in drivers;

One process can start the same method several times with different arguments, to compute different parts of the data. Next example starts one method in a loop. Every started method writes its own element of the array s: two started methods never receive the same output variable. After the method starts several times, the process waits for the group demo to finish.


## create parallel work
driver parallel_loop is

  ** compute one result
  method square(n: Integer, @result: Integer) is
    result := n * n;
  return;

  process main is
    let s: [4]Integer; ** one result for each worker

    ** start the same method 4 times
    demo: parallel
    do
      for i in (1..4) do
        start square(i, @s[i]); ** runs in parallel
      done;
    done demo;
    ** all started methods have finished, s is ready
    print s; ** [1,4,9,16]
  return;
end parallel_loop;

Note: Groups bring the process back in synchronous mode. That is good for error handling. If a started method raises an error, the methods of its group that have not begun are cancelled, the running ones finish, and the error is raised by done. The next groups do not begin, so a recover region can catch the errors of all the started methods.

Exception Handlers

An exception is an object that has methods. The EVE system defines several system variables and system objects used to handle exceptions. In Eve, all exceptions are considered errors. We can monitor jobs using a log and record exceptions in this log. Exceptions from one aspect process can propagate to the main process.

The "$error" is a variable of type Exception.Error that is created when an exception is raised. It alwais point to last error of a process. The system variable $trace contains several elements that are errors. These are filled in by the Eve program when an exception is raised. If an error is raised from a recover region it will propagate in the main process.

Error handling in Eve is done at process level, in the recover region. A process can be interrupted by a system exception or it can create user-defined exceptions. We use special keywords to signal an exception from inside a job: {raise, expect}.

Pseudocode

The Exception module is not yet created. We have the intention to use Eve to create this module. Next is a prototype that explain the structure of future Exception module. It define class .Error that is public and several metods.

** system exception type
module Exception is

  class .Error: {
    code: Integer,
    message: String,
    module: String,
    line:Integer
  } <: Object;

  class .Error = {code: Integer, message: String} <: Object is
    constructor(@self)(code, message) is
      self := new Object();
      let self.code := code;
      let self.message := message;
    return;
  end Error;

  class Call = {line:String, method:String} <: Object is
    constructor(@self)(line, method) is
      self := new Object();
      let self.line   := line;
      let self.method := method;
    return;
  end Call;

  ** system variables
  set $error: Error;   ** last error

  ** system objects;
  set $stack: ()Call;  ** list of calls
  set $trace: ()Error; ** list of errors

  ** methods for Exceptions
  method (@self:Error) .raise(...);
  method (@self:Error) .expect(...);
  method (@self:Error) .pass(...);
  method (@self:Error) .fail(...);

end Exception;

Runtime Errors

Runtime errors can be system exceptions or user defined exceptions. System exceptions are predefined in the Exception package. Every system module can define system errors. User errors can be defined in project library.

Raising exception

Error instances are created during the process execution when a process can not continue. An error can be raised by application modules, aspects or drivers or by the system modules. Developer can create errors. These are called "runtime errors" because they are not "syntax errors".

There are two alternative statements to create user defined exceptions: {raise, expect}. These are public/static methods defined in Exception module. You can raise exception from jobs, methods, methods and functions.

Syntax: 

** system exception
raise $ExceptionType("message");

** user-defined exception
raise (code,"message") if condition;

Using expect

The "expect" statement can check a condition and raise an error if condition is false. Error message is default: "Unexpected error in line: N". Optional you can define a custom message.

Pattern:

** runtime expectations
expect condition1;
expect condition2, "user defined message";

Nots:

  • can be used as inside any block statement inlcuding jons, loops or decision blocks
  • can be used as post-condition after jobs before the recover region in any process
  • Exception create one single type of error: implicit error is AssertError

Recover from exception

Jobs do not handle exceptions. An error raised in a process, inside a job, in a method it calls, or between jobs, interrupts the process, and the workflow jumps into the recover region.

In the recover region the developer uses normal control statements (if, match) and the $error system variable to decide what to do next, and ends with one of these statements:

StatementEffect
retryrun the failed job again, from the start of its declarations
resumethe error is handled: the job stays failed and the process continues after its done
abortend the process: the finalize region runs, then the error propagates to the calling process
  • If the recover region ends without one of these, the error is handled: the finalize region runs and the process ends normally.
  • retry and resume need a failed job. An error raised outside any job can only be aborted.
  • Raising another error in the recover region aborts with the new error.
  • A process without a recover region aborts on every error. If the driver aborts, the application ends with an error exit code.
  • retry can repeat forever: count the attempts in a local variable.

Aspect processes should handle as much as possible to keep the concerns local. Main process can handle the general case just in case but can also just not have a recover or finalize region.

Example:

#using recover
driver recover_demo is
  set a = 0.00;
  process main is
    a := 1/0;
  recover
    print $error.message;
  return;
end recover_demo;

Output:

error: numeric division by zero.

Finalize

The finalize region is optional. It runs once, when the process ends: after return or exit, or after the recover region has aborted. It is skipped by over and panic. After retry or resume the process continues, so finalize runs later, when the process ends.

In finalization region developer can close resources, tear down data of test cases, archive the logs, send signals, prepare output parameters or just print debug messages. Whatever is required after all code is execute just before process termination.
